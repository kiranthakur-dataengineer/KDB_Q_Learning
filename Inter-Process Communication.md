# Introduction

Inter process communication is essential and a fundamental part of real-world applications using 
kdb+. Kdb+/q conveniently has a built in method of connecting to other kdb+/q processes to retrieve 
and/or manipulate data.


## IPC Protocol 

Interprocess communication between kdb+/q processes uses the 
[TCP](https://en.wikipedia.org/wiki/Transmission_Control_Protocol)/[IP](https://en.wikipedia.org/wiki/Internet_protocol_suite) protocol. 


# Connecting to Processes

When we claim a port for our process (.e.g this process is currently running on port 8888), we are 
creating an address for our process which can now be connected to by other processes. 

## Listening on a port
If you wish for other processes to be able to connect to your q process, you must tell your process to listen on a port. 

To do this, you have two options:


* Start the q process with a predefined port as follows -

    ```myprompt$ q -p 5010		// this will start q and tell it to listen on port 5010 ```

* Within a running q process (such as this one) we can assign or change the port as follows - 

    ```q)\p 5020          // tells q to listen on port 5020```
    

We are running this training using Kx Developer, which already has a port assigned: 

```q
//let's check the current port associated with this process
\p
```

Other q processes can connect to ours using this port! 

## Connecting to a port

Connections to processes are formed by using the [`hopen`](https://code.kx.com/q/ref/hopen/) command in conjunction with our process address. 


### IPC and `hopen`

Connecting to another process using `hopen`.

The base syntax is as follows: 

    hopen `:<computer host/IP>:<port number>:<username>:<password>
    
Though some of these can be omitted if we are connecting to processes on the same host, or if the 
process doesn't have any authentication checks:

    hopen `:localhost:<port number>   //localhost is understood
    hopen `::<port number>            //this is valid - localhost is assumed when a host isn't provided
    hopen <port number>               //this is also valid - assumes localhost
    
We started a background q process when we loaded our repository (you can see the log messages 
that documented this in your console). 

More generally, if we did want to run a process in the background the syntax is: 

    //starting a background q process to run myQScript.q on port 5010

    system["nohup q *PATH_TO_SCRIPT* -p *PORT* >*OUPUT_TO_HERE* 2>&1 &"]
    
The background process is running the q script `remoteProcess.q` which we can see in the IPC.Scripts
module. This has some in-memory tables which are generated by the script and we can see from our 
logging the port on which it was started.

Focusing on this process, lets open a connection: 

```q
show h: hopen 5050
```

Success! 


## Active Connections

The handles dictionary stores the current open connections associated with the number of bytes 
in their output queues.

We can use this to check if our previous handle `h` is still open: 


```q
.z.W
```

```q
h in key .z.W
```

We can see open handles will be added and removed once closed:


```q
show h: hopen `::5050  //opening another connection
```
```q
.z.W
```
```q
h in key .z.W          //our handle is open and in the dictionary key 
```

```q
hclose h               //closing
h in key .z.W          //our handle is closed and not in the dictionary key 
```
```q

```


# Methods of executing across a handle
We introduced the methods of executing using a handle in the previous section, but here we delve into this more deeply. 



## Symbol execution 
The most simplistic and limited method to retrieve data from a connection is to use the symbol reference: 


```q
h `quote
```

## String execution 
More flexibility in execution can be achieved if we use the string method: 


```q
h "tables[]"
```
```q
h "select count i by sym from trade"
```

And then join that to our query:

```q
show "select from trade where sym in ","`","`" sv string symList  //as a string
h "select from trade where sym in ","`","`" sv string symList     //sending to the remote process
```

String execution is useful for quick ad-hoc queries, but trying to use this method in a more 
dynamic/functional way isn't very readable, or extensible - luckily there is a better way! 

## Functional/Parse tree execution
In cases where we wish to send information to the remote process the functional, or parse tree 
form is far more useful. 

Let's examine an instance where we want to send a table to our remote process and define it there.  


```q
5 sublist t: 10000#([]a:1 2 ; b: 20 30)   //a local table  
```
```q
h (set;`tab;t)     //sending to define remotely using set 
5 sublist h "tab"  //retrieving back using the string method 
```

```q
//sending a function for remote execution 
h ({x+y};2;3)     //syntax: <handle> (<function>;<param1>;...;<param8>) 
```

### Passing by Reference versus Value


The function `myFunc` is defined on the remote process as follows: 

```q
h "myFunc"
```

Let's define this also on our notebook process as having a different behaviour: 


```q
myFunc: {x-y}    //subtraction rather than addition. 
```

If we pass the function name as a symbol, this symbolic value is used to retrieve the value associated 
with this variable name on the remote process. 

If we don't use the symbol name we are instead sending the function definition directly to the 
remote process. 


```q
h (myFunc;1;2)    //sending our function by value - equiv ({x-y};1;2) 
```
```q
h (`myFunc;1;2)   //sending a reference symbol - this will be retrieved on the remote process 
```

# Synchronous and Asynchronous messaging
Up until now we have executed all our code synchronously on the remote server, but there are 
actually two ways to send messages to a server - synchronously (aka "sync") or asynchronously 
(aka "async").

## Definitions

### Synchronous messaging 

A positive handle value will execute synchronously. This will wait for a result to return.
 

    h       //the positive handle value will execute synchronously 


### Asynchronous messaging

An asynchronous message does not return a result or wait for the code to finish execution.

    neg[h]  //the negative handle value will execute asynchronously 

[comment]: <> (<img src="../qbies.png" style="width: 50px;padding-right:5px;padding-top:2px;padding-left:5px;" align="left"/>)

For example, a `delete` or `insert` statement can be sent asynchronously


## Difference
   
 
Let's look at two simple examples - in one we will execute a function with a return on our remote process (showing execution return) and in the second we will simulate waiting for a function to complete (showing our wait for a response): 


```q
//function return
h (+;1;1)      //when we call this for execution we get our value back 
```


```q
//function does not return to this process (though execution occurs remotely)
neg[h] (+;1;1)  //we don't actually get any return
```


```q
//waits for response 
h ({system "sleep 5"};())
```


```q
//does not waitfor response 
neg[h] ({system "sleep 5"};())  //NOTE: the remote process does in fact sleep for 5 seconds 
```

All functions sent to the remote process are still executed there, but our process is free to continue with other activities in the meantime.

# Attaching to remote processes

Most IDEs (including this one) offer the ability to connect and "attach" to a remotely running 
q process. When you are "attached" like this, statements executed in the IDE are automatically sent
to the remote process and executed there. 

Let's open a remote scratchpad to our process running on port 5050:
    
- Tools->Remote Scratchpad (Top Left Side of the screen). 
- Click on New. 
- You will now be prompted to enter a Name and a port number 
- Now click on Attach to connect to this process. 


Let's create a list of 10 elements on the remote process. Open the remote scratchpad and connect it to the process running on port 5010.

```q
server_list : 3+til 10  // Copy this and run it on the remote scratchpad
```

We can get this list in the client service by the following command.

```q
h `server_list  
```

When we are complete with our querying we can close the handle and end the connection.


```q
hclose h 
h "2+2"           //now our handle is closed we can no longer use it to access the background process
```
